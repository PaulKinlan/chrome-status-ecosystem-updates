# OpaqueRange

> **Report Week:** 2026-W41 | **Milestone:** Chrome 152 | **Category:** Enabled by default

## Overview

\`OpaqueRange\` represents a live span of text within a form control’s value, such as a \`&lt;textarea&gt;\` or text-based \`&lt;input&gt;\`, so developers can work with value text using range-like APIs.  It enables operations such as \`getBoundingClientRect()\`, \`getClientRects()\`, and integration with the CSS Custom Highlight API for UI such as inline suggestions, highlights, and anchored popovers. It preserves encapsulation by exposing only value offsets while returning \`null\` for \`startContainer\` and \`endContainer\`, so DOM endpoints and internal structure are not exposed.

### Motivation

Currently, developers can’t get accurate text geometry or apply the CSS Custom Highlight API to text inside native `<textarea>` and text-based `<input>` controls.

As a result, they often avoid native form controls and build editable `<div>`-based workarounds to anchor UI, such as autocomplete popovers, or to highlight matches. These workarounds require reimplementing native editing behavior and can have accessibility gaps.

`OpaqueRange` enables range-based operations on the control’s value text, so developers can measure text geometry and build text-anchored UI directly in native controls.

## Ecosystem Status

- **Momentum:** High (400 points)
- **Standards Alignment:** Multi-Engine Consensus
- **Sentiment:** Positive
- **Executive Take:** OpaqueRange has shipped enabled by default in Chromium 152 (Chrome and Edge), addressing a long-standing web platform gap by enabling live text ranges, geometry measurement, and CSS Custom Highlight API styling within native form controls. The specification has achieved broad vendor consensus across the WHATWG, W3C TAG, Mozilla, and Apple, eliminating brittle mirror-\`&lt;div&gt;\` and custom \`contenteditable\` workarounds. While currently limited in production to Chromium, active implementation in Gecko and WebKit points toward imminent multi-engine baseline support.

### Recommendations
- Actionable Advice: Adopt OpaqueRange using progressive enhancement by feature-testing \`'createValueRange' in HTMLInputElement.prototype\` or checking the global \`window.OpaqueRange\`. Teams building caret-anchored suggestions or inline highlights should deploy native form controls with OpaqueRange for Chromium users while retaining mirror-element fallbacks or polyfills for Safari and Firefox until their implementations reach stable.
